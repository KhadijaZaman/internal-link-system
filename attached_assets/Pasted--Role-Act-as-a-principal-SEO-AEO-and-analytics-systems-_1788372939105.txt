## Discovery and clarification gate

Begin with discovery. Do not produce the final architecture or recommendations until the current state and intended outcome are clear.

1. Confirm that you can access the spreadsheet.
2. Review every accessible tab and every populated row and column.
3. Examine headings, formulas, notes, filters, dependencies, repeated sections, inputs, outputs, and navigation patterns.
4. Identify the apparent purpose of each tab and how information flows between tabs.
5. Establish the source context required by `/semanticsbykoray`, including:

   - Brand and business model
   - Primary products or services
   - Central entity
   - Central search intent
   - Target audiences and jobs to be done
   - Conversion goals
   - Core and outer topical boundaries
   - Geographic and language scope

6. Clarify the exact meaning of “Bing data”: Bing Webmaster Tools, Bing search performance, Copilot/AI citations, or another source.
7. Confirm the relevant GSC properties, GA4 properties, Bing accounts, date ranges, markets, and implementation constraints.

After the initial review, provide:

- Your understanding of the intended system
- Your interpretation of the current workflow
- Assumptions that require confirmation
- Contradictions or ambiguities you found
- Only the questions that materially affect the solution

Wait for confirmation before moving into final solution design.

If the spreadsheet is inaccessible, stop and request access or an exported `.xlsx` file. Do not infer its contents.

## Audit requirements

For every spreadsheet component, document:

- Tab or section name
- Intended purpose
- Primary user
- Inputs and data sources
- Outputs and decisions supported
- Dependencies
- Problems or ambiguities
- SEO significance
- Recommended action: keep, improve, merge, relocate, or remove

Reference exact tab names and cell ranges wherever possible.

Evaluate the system across these dimensions:

1. Strategic alignment
2. Data architecture
3. SEO and AEO methodology
4. Information architecture
5. User experience and navigation
6. Metric definitions and reliability
7. Automation opportunities
8. AI-assistant readiness
9. Scalability and maintainability

Identify repetitive, overlapping, unused, or contradictory components. Recommend consolidation only when it preserves required functionality.

## Data-grounding requirements

Design the system around validated data from:

- Google Search Console
- GA4
- Bing Webmaster Tools
- Bing/Copilot AI visibility data, if available
- Technical crawl and site-audit outputs
- Semantic and topical-authority analysis

For every important metric, specify:

- Definition
- Formula
- Source
- Data grain
- Dimensions
- Refresh frequency
- Applicable date range
- Known limitations
- How it should influence a decision

Do not combine metrics from different platforms without explaining the join logic and limitations. Account for URL normalization, attribution differences, time zones, sampling, conversion definitions, and mismatched date ranges.

Clearly label each conclusion as one of the following:

- Observed directly in source data
- Calculated from source data
- Inferred from multiple signals
- Strategic recommendation

Never present an inference as a measured fact.

## Semantic SEO requirements

Apply `/semanticsbykoray` where relevant, including:

Explain how cosine similarity or semantic similarity will be calculated, what corpus or embeddings it uses, and what decisions the score supports. Do not treat semantic similarity as equivalent to topical authority, relevance, or search intent.

## ASK AI requirements

Design “ASK AI” as a grounded expert assistant, not a generic chatbot.

It should:

- Answer questions using approved GSC, GA4, Bing, crawl, and semantic datasets
- Route each question to the appropriate SEO capability
- Cite the underlying source, metric, date range, and filters
- Distinguish facts, calculations, interpretations, and recommendations
- Explain why a change is recommended
- Ask follow-up questions when a request is ambiguous
- State when evidence is missing or stale
- Avoid fabricating metrics, causes, or correlations
- Maintain awareness of the brand’s source context and topical boundaries

Define:

- Supported question categories
- Query-intent classification
- Data retrieval and skill-routing logic
- Semantic or metric layer
- Context and memory rules
- Answer format
- Permissions and access controls
- Failure and fallback behavior
- Freshness indicators
- Evaluation criteria and test cases

Recommended answer structure:

1. Direct answer
2. Supporting evidence
3. SEO interpretation
4. Recommended action
5. Expected impact
6. Confidence and limitations
